## Description

As the owner, I want to see every publish attempt the app has made — dry-runs and live posts — in one place, with which video file each one approved, so that I can answer "what did the app post, where, when, and was it real?" without opening SQLite or `audit.jsonl`. Restart plan Phase 1 item 8 (`docs/roadmap/LANDSCAPE-AND-PLAN-2026-10-24.md` §5). Today the only reader is `GET /api/projects/{id}/audit` (one project at a time, no UI). Since S-3.3.8 (2026-11-03) every row carries `render_content_hash`, so a row can be tied to its file.

## Acceptance criteria

- [x] An app page (Dashboard link or Settings section) lists audit rows across all projects, newest first: time, project, snapshot, platform with a clear dry-run / live marker, visibility, external URL (link for live posts), response code, approval token and a short render hash
- [x] A row links to its snapshot's Inspect view, and shows whether the render file on disk still matches the recorded hash
- [x] The backend serves the cross-project list through one paginated endpoint (token-protected like the rest of `/api`, ADR-0022)
- [x] Tests: endpoint ordering and pagination; vitest for the dry-run / live marker and the hash-mismatch state

## Notes

Two rows exist as of 2026-11-03, both `youtube (dry-run)` on the Zion project; row 2 is the first with a render hash.

Shipped 2026-11-08 as `GET /api/audit?limit=&offset=` (limit 1–200, default 25; `{items, total, limit, offset}`) and the **Publish log** page at `/publish-log`, linked from the Dashboard. Each row's `render_check` is `match` / `changed` / `missing` / `unrecorded` (no hash recorded, i.e. older than S-3.3.8); the current render is hashed once per file version (cached by path + mtime + size), so paging does not re-read the videos.
