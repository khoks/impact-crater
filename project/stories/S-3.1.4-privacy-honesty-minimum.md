## Description

As a user who sends my family's photos through a remote AI, I want the app to tell me plainly what leaves my machine and to guarantee the one thing it can guarantee today (downsized renditions with no location or camera data, never the original file), so that the Settings copy is true and I am not shown controls that do not exist. Today `media/privacy.py` ships `strip_exif`, `blur_faces` and `prepare_for_llm` with zero call sites in `api/`, `pipeline/` or `jobs/` (grep 2026-10-24); Stage 3 reads `thumb_1024_path or source_path` (`pipeline/stage3_metadata.py:208-211`), so the full-size original is the silent fallback when a rendition is missing; renditions are re-encoded by Pillow (`pipeline/stage1_ingest.py:243`), which happens to drop EXIF, but nothing asserts it; `frontend/src/routes/Settings.tsx:151-160` shows hard-coded read-only toggles and leaks "LLM", "ADR-0016", "E-2.6" and "recognized_persons=[]" to the user, and `Setup.tsx:332` cites ADR-0016. This is the Phase 2 minimum (restart plan §5 Phase 2 item 7); privacy *routing* and the full three-toggle per-project matrix are Phase 5 (S-3.1.3).

## Acceptance criteria

- [ ] `strip_exif` (or an equivalent explicit call) runs at the rendition-creation point in Stage 1 before the 256/1024 px JPEGs are written; a regression test feeds a source with GPS + orientation + maker-note tags and asserts the renditions carry no EXIF/XMP/GPS bytes while orientation is applied, not carried
- [ ] Stage 2/3 never send an original: the `thumb_1024_path or source_path` fallback is removed or becomes a classified failure with a readable reason; a test proves a missing rendition does not fall back to the source file
- [ ] Settings and Setup replace the hard-coded read-only toggle list with a plain-language "What we send to the AI" panel (downsized copies without location/camera data; faces are not blurred; which providers receive them; link to the privacy doc); no "LLM", "ADR-0016", "E-2.6" or "recognized_persons" strings remain in user-visible copy under `frontend/src` (vitest asserts)
- [ ] Blur-faces becomes a real toggle only once a working detector lands (OpenCV YuNet, restart plan Phase 2 item 10); until then the panel states faces are not blurred. When it lands, the toggle applies `blur_faces` CV-only to the rendition before it is sent — no routing change
- [ ] `docs/OVERVIEW.md`'s privacy section states exactly this and promises no more than the S-3.9.4 delete path honours (S-2.13.4's public-trust pass is the baseline this story edits)
