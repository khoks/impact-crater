## Description

As a user, I want the app to detect once, at setup, what my machine can run (GPU vendor and class, VRAM, system RAM, CPU cores, OS) and remember it, so that local backends — the image-embedder device (S-2.10.8), the Ollama runtime tier (S-3.1.1), the insightface cast backend suggestion and local crowd-removal eligibility (S-2.9.7) — are chosen for me and I never pick a model, as the mission and ADR-0008's hardware-tier mapping promise. Today no probe exists: a grep of `backend/impact_crater` for vram / gpu / cuda finds only two comments (`media/face_embed.py:120` hard-codes CPU `ctx_id=-1`; `media/image_embed.py:7`), and `storage/settings.py` holds `cast_backend` / `image_embed_backend` keys with no auto-suggest rule. The restart plan sequences this first in Phase 3 item 2 ("Hardware probe + real local image embedder"), ahead of the Ollama runtime in Phase 5 (landscape §4.3 #19 / #21: embedder-first, runtime-second).

## Acceptance criteria

- [ ] `hardware.probe()` returns `{gpu_vendor, gpu_name, vram_gb, ram_gb, cpu_cores, os, cuda_available}` without importing torch when it is absent (nvidia-smi / `psutil` / platform APIs), completes in under 2 s, and never raises (unknown → `None`)
- [ ] The result is persisted in settings at setup (new keys) and refreshable from a Settings "Re-detect hardware" action; shown read-only in Setup and Settings in plain language ("Your machine: NVIDIA 12 GB — local image analysis available")
- [ ] A `hardware_tier` per ADR-0008 (no-GPU / 8–12 GB / 16–24 GB / 32+ GB) is derived from the probe and consumed by S-2.10.8 (cuda vs cpu; ViT-L/14 vs ViT-B/32), by S-3.1.1 (runtime tier → model size under the ≤ 32B cap), by the insightface auto-suggest rule (suggest when a GPU or ≥ 16 GB RAM is detected — never silently default, per landscape §4.3 #23 and the licensing D-NNN), and by S-2.9.7 for the `local` inpainting tier
- [ ] Tests with a stubbed probe cover each tier boundary, the no-torch path and the no-GPU path on both Windows and Linux

## Notes

The hardware-tier ADR the plan defers ("write the hardware-tier ADR then") is written with S-3.1.1 once real probe data from the owner's machine exists; this story only supplies the data. The NotebookLM assets already assert "hardware-adaptive processing" (landscape §4.2) — this is the first code that would make the claim true. Local backends (`insightface`, `torch`, `onnxruntime`, `open_clip`) are not installed on the dev machine, so the probe must also report which optional packages are importable so the bootstrap can install them deliberately.
