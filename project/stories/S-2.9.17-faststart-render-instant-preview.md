## Description

Filed 2026-06-18 on the premise that the Stage-7 ffmpeg mux wrote the `moov`
atom at the end of the mp4 (no faststart), so an inline `<video>` without
autoplay stalled at `readyState=0`/`networkState=2`. The premise was false:
`-movflags +faststart` has been in the final mux (`pipeline/stage7_render.py:524`,
`_mux_video_audio`) since the Stage 6-7 render landed on 2026-05-04 (PR #14,
5e939ee). The stall actually observed was the `Content-Disposition: attachment`
header that `FileResponse(filename=…)` emits by default — Chrome refuses to play
attachment responses inside a `<video>` element — and PR #40 (bfbb029,
2026-06-10) fixed it with `content_disposition_type="inline"` in
`api/snapshots.py` `get_render`.

What remains unverified is whether the render endpoint serves HTTP Range
requests. Browsers fetch the first frame and seek with `Range:` headers and
expect `206 Partial Content`; `api/snapshots.py` has no explicit Range handling,
so first-frame latency and seeking depend entirely on starlette 1.0's
`FileResponse` honouring `Range` (pinned `starlette==1.0.0` in
`requirements-lock.txt`). That has never been checked against a real
`render.mp4` from `SnapshotInspect`, `JobPreview` or the dashboard player.

## Acceptance criteria

- [x] Stage-7 render passes `-movflags +faststart` to the final mux. — verified by stage7_render.py (flag present since 2026-05-04) (2026-10-24)
- [ ] `SnapshotInspect` / preview `<video>` shows the first frame promptly (no indefinite spinner) — includes confirming that `GET /api/snapshots/{id}/render.mp4` answers a `Range:` request with `206 Partial Content` on starlette 1.0 (e.g. `curl -r 0-1023 -D -` against a real render, then a seek in the player), and adding explicit Range handling if it does not.
- [ ] No regression in render size/quality or YouTube upload. — superseded by re-scope (2026-10-24)
