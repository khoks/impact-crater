## Description

Jobs live only in the in-memory `JobRegistry`, so a server/computer restart
loses the live job object — the `/jobs/:id` (in-progress) and `/jobs/:id/preview`
routes 404 afterward. S-2.9.16 added a snapshot-keyed Inspect & Feedback view as
a workaround (render + diagnostics are persisted by snapshot_id). The deeper fix
is to make jobs themselves durable: persist the registry, or reconstruct
completed jobs from the DB `snapshots` table on startup, so the live and preview
views survive restarts natively (per A-025).

## Acceptance criteria

- [ ] Job state (or enough to rebuild it) is persisted, or finished jobs are reconstructable from the `snapshots` table on startup.
- [ ] After a restart, `/jobs/:id/preview` resolves for a finished job without re-running.
- [ ] In-progress jobs interrupted by a restart are handled gracefully (resume-from-cache messaging, not a silent 404).

## Dependencies

- A-025 (capability), S-2.9.16 (snapshot-keyed workaround it supersedes for the finished-job case).
