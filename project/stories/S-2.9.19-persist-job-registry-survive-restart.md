## Description

Jobs live only in the in-memory `JobRegistry`, so a server/computer restart
loses the live job object — the `/jobs/:id` (in-progress) and `/jobs/:id/preview`
routes 404 afterward. S-2.9.16 added a snapshot-keyed Inspect & Feedback view as
a workaround (render + diagnostics are persisted by snapshot_id). The deeper fix
is to make jobs themselves durable: persist the registry, or reconstruct
completed jobs from the DB `snapshots` table on startup, so the live and preview
views survive restarts natively (per A-025).

## Acceptance criteria

- [x] Job state (or enough to rebuild it) is persisted, or finished jobs are reconstructable from the `snapshots` table on startup.
- [x] After a restart, `/jobs/:id/preview` resolves for a finished job without re-running.
- [x] In-progress jobs interrupted by a restart are handled gracefully (resume-from-cache messaging, not a silent 404).

## Notes

- 2026-11-08 implementation: migration `008_jobs.sql` adds a `jobs` table holding each `JobSnapshot` as JSON. `JobRegistry` saves on `register`, every `update_state` and every `update_stage` (cost counters move on each LLM call but are saved at the next stage or state change, so a reloaded job's cost is exact for finished jobs and at most one stage behind for interrupted ones). `get_or_load` reloads a job the current process has not seen (used by `GET /api/jobs/{id}`, cancel and the WebSocket, which then replays the terminal state and closes). `recent(20)` backs `GET /api/jobs`, so the Dashboard's "Recent jobs" survives a restart. At startup the lifespan calls `recover_interrupted`: every saved `queued` / `running` job becomes `failed` with `INTERRUPTED_REASON` (re-run, it resumes from cache) and its running stage `failed` with "interrupted by a server restart". `submit_full_pipeline_job` is now async and validates `mode` before registering.
- Not done here: per-stage checkpoints for a true mid-stage resume (a re-run already resumes cheaply through the content-hash LLM cache), and marking the June orphans "abandoned" in telemetry (telemetry is keyed by the correlation id, which a job learns only when the pipeline returns). The three June 2026 orphans predate the table, so they stay invisible to it.
