## Description

As a user running the app on my own machine, I want nothing else on my network — or any page in my browser — to be able to read my folders, change my settings, spend my API budget or publish on my behalf, so that exposing the app for an Instagram public URL or a remote device never means exposing the API. Today no route and not the WebSocket (`api/jobs.py:400`) checks authentication or origin (grep of `backend/impact_crater/api/*.py` and `app.py` for Authorization / bearer / origin finds nothing); `cli.py:71` accepts any `--host` with no warning; the folder-scan endpoint (`api/folder.py`) resolves and reads any absolute directory; settings, setup, job submit, render, refine, publish, feedback, persons and workplan all mutate or spend; there is no `SECURITY.md`. Restart plan §5 Phase 1 item 3b; landscape §4.2 "Local API hardening", §4.3 #39 (default: loopback-only + flag + token, built before any tunnel).

## Acceptance criteria

- [x] A per-install random bearer token is generated at first start, stored under `~/.impact-crater`, injected into the SPA (served HTML or a loopback-only bootstrap endpoint) and required — 401 otherwise — on every mutating route (POST/PUT/DELETE across settings, setup, jobs, render, refine, publish, feedback, persons, workplan) and on the WebSocket handshake; GET media/thumbnail/render routes are either tokened or documented as loopback-only — verified by `tests/test_api_auth.py` and live on 2026-11-03: the built page carries the token meta tag for loopback clients, Settings → Save changes went through (200), an unauthenticated POST got 401, and the Vite dev page fetched `/api/session` once; loopback reads stay tokenless and are documented in SECURITY.md / ADR-0022 (2026-11-03)
- [x] The WebSocket rejects a non-matching `Origin`; CORS stays same-origin — verified by `test_websocket_from_a_foreign_origin_is_refused` (1008) and live through the Vite proxy (Origin `localhost:5174` accepted, `ws_unknown_job` after auth); no CORS middleware (2026-11-03)
- [x] `impact-crater --host <non-loopback>` refuses to start without `--allow-remote` and prints the exposure warning; `--allow-remote` still requires the token — verified by `test_non_loopback_host_without_allow_remote_refuses_to_start` (exit 2) and `test_remote_client_needs_the_token_even_to_read` (2026-11-03)
- [x] `SECURITY.md`: how to report, the threat model (single-user local app), what the token does and does not protect, Fernet key location and the key-management guidance from S-2.13.5 — verified by SECURITY.md (2026-11-03 revision) + ADR-0022 (2026-11-03)
- [x] Tests: unauthenticated POST → 401; WS without token or with a foreign origin → closed; `--host 0.0.0.0` without the flag → non-zero exit; the frontend fetch wrapper attaches the token (vitest) — verified by `tests/test_api_auth.py` (13) and `frontend/src/__tests__/apiClient.test.ts` (2) (2026-11-03)

## Notes

Hard prerequisite, not a nice-to-have: the Instagram tunnel the connector needs would expose the unauthenticated API today (landscape §5 "Risks"). The signed-media-URL design belongs to the Instagram public-URL decision (Phase 4) and is only named here as the constraint this story enables. Keep the token out of URLs (query strings leak into logs); use a header, and for the WS the first message or a cookie bound to loopback.
