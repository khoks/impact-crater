## Description

A 1,663-file validation job surfaced three issues, found via a 5-agent code
investigation (adversarially scoped):

1. **Cost metering under-counted ~5×** (app recorded $6.93 of Anthropic Sonnet;
   Anthropic billed ~$34.09). Root cause: `LLMRouter._record_call` priced every
   call with a flat per-tier **ballpark** (`_TIER_COST_FALLBACK`, $0.005/call for
   Tier-M) and **discarded the API responses' real token usage** (`input_tokens`/
   `output_tokens` hardcoded to 0; image tokens ignored). The correct
   `rate_cards.estimate_cost_usd()` existed but was only called in tests. With a
   broken meter the spend cap was effectively blind.
2. **Opaque failure on credit exhaustion.** The job died at the Stage-5 Opus
   judge with a raw `400 … 'Your credit balance is too low …'` dumped verbatim
   into `failure_reason`.
3. **Stage-2 progress bar overflowed** ("7,500 / 6,652"): the denominator was
   `media_count × 4` (input files), but videos split into scenes, so the real
   shot count (2,067) exceeded it.

Also: raised the daily spend cap from $50 → $100 (runtime setting) since jobs of
this size legitimately cost more than $50.

## Acceptance criteria

- [x] Each provider client writes the API's real token usage onto the per-call `CallParams` (`AnthropicLLMClient._call_messages` → `_apply_usage`; `GoogleLLMClient` generate_content sites → `_apply_usage`).
- [x] `LLMRouter._record_call` prices from those tokens via `rate_cards.estimate_cost_usd()`, falling back to the ballpark only when usage is absent (cache hits, embeddings, test fakes); emits real `input_tokens`/`output_tokens` in `LLMCallEvent`.
- [x] Anthropic "credit balance is too low" (and rate-limit / auth) 400s are classified into a concise, actionable `failure_reason` (`runner_glue._classify_failure`) — keeps the raw string as fallback; full traceback still logged.
- [x] Stage-2 progress uses the true post-scene-split shot count: runner reports it in the Stage-2 detail (`N shots …`); frontend parses it as the denominator and clamps the numerator so it never reads >100%.
- [x] Daily total spend cap raised to $100 (via `POST /api/settings/update`).
- [x] Regression test (`test_cost_uses_real_token_usage_not_flat_ballpark`) + targeted suites green (74 backend + new test); frontend build + JobInProgress tests green.

## Dependencies

- ADR-0015 (cost/rate-card model), ADR-0009 (tiering)
- Rate cards already correct in `config/rate-cards/` — they were simply never used in the production cost path.

## Notes

The pre-job *estimate* (`_estimate_cost_per_provider` / cost-preview) is a
separate, pre-call estimator and was not changed here; making it token-aware is
a follow-up. Past under-recorded `quota_state` spend is historical; new calls
record accurately.
