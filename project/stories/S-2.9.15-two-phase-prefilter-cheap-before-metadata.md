## Description

Today the pipeline runs **Stage 3 rich-metadata extraction (Tier-M Sonnet) on
all surviving assets, then Stage 4 pre-filter** narrows them. On the 1,663-file
validation job, Sonnet metadata ran on ~1,422 shots but pre-filter then kept
only 621 — so we paid for expensive rich metadata on ~800 shots that were
immediately dropped (~half the Tier-M spend wasted).

A naive reorder (pre-filter before metadata) is **NOT safe** — investigation
confirmed Stage-4 pre-filter *depends* on Stage-3 metadata: the safety floor
(drops explicit frames), obstruction filtering, location/time-of-day clustering,
specialness ranking, and the `metadata_summary` the Opus judge reads. Dropping
those would lose safety + curation intelligence.

The correct optimization is a **two-phase pre-filter**:
1. **Cheap pass** using only Stage-2 signals (quality_score, narrative_relevance,
   perceptual-hash dedup, embedding semantic dedup) to cut obvious
   duplicates/low-quality — no Stage-3 dependency.
2. Run **Stage-3 rich metadata on the survivors only**.
3. **Full metadata-aware pre-filter** (safety, obstruction, location/time
   clustering, specialness, metadata_summary) → final candidate set for Stage 5.

This preserves all safety + intelligence while roughly halving Tier-M cost on
large jobs. Directly serves the user's cheap-first vision (A-016).

## Acceptance criteria

- [ ] Refactor pre-filter into `prefilter_cheap` (Stage-2-only: quality floor + relevance + phash + embedding dedup) and the existing full metadata-aware pass.
- [ ] Runner sequence: Stage 2 → cheap pre-filter → Stage 3 metadata (survivors only) → full pre-filter → Stage 5.
- [ ] No regression in curation quality vs the current order (validate on the Zion/SW-US set; compare candidate sets + final render).
- [ ] Measure and report the Tier-M cost reduction.
